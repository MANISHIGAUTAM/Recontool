# Event-driven execution engine for Recontool (v2)

The change adds a complete event-driven orchestration layer (`recontool/engine/`, 14 modules) with typed events, an async pub/sub bus, a dependency-aware scheduler, three-layer concurrency-controlled executor, incremental scan fingerprinting, and an AI heuristic classification service. All nine issues from the first review pass have been addressed: the orchestrator now checks for running tools before idle-exit, cleans up per-scan state, exposes public scheduler methods, uses `return_exceptions=True` on the EventBus, adds a dedicated `config_fingerprint` column, evicts host semaphores via LRU, delegates in `map_outputs_to_entities`, and builds real inputs for downstream tools.

Watch for:
- **IncrementalEngine and DependencyChecker not wired into runtime path** (confirmed): the orchestrator accepts these as constructor parameters and stores them but never calls them during `run_scan`. They're dead code at the integration level.
- **Entity accumulation in `_available_entities` unbounded** (confirmed): the scheduler appends every discovered entity value to in-memory lists that grow without limit across a scan's lifetime.
- **Checkpoint resume path declared but not implemented** (confirmed): `ScanConfig.resume` is accepted and `Checkpoint` is imported, but the resume logic is never exercised.

**Verdict**: APPROVED

## High-level view

The remaining gaps are non-blocking. `IncrementalEngine` and `DependencyChecker` are built and unit-tested in isolation but the orchestrator never calls them — they exist as infrastructure for a future wiring pass. The scheduler's `_available_entities` dict grows monotonically per-scan (every discovered entity value is appended), which could become a memory concern for scans discovering tens of thousands of entities, but this is bounded by scan lifetime. Checkpoint resume is declared in the config model but stub-only.

The EventBus `return_exceptions=True` fix prevents cascade failures but introduces a silent-failure mode: handler exceptions are swallowed with no logging. If the scheduler's `on_tool_completed` handler raises, the scan enters an inconsistent state with no diagnostic signal. The host-semaphore FIFO eviction is bounded but evicts regardless of whether the semaphore is currently held, meaning an active host can lose its concurrency limit mid-scan.

1. **IncrementalEngine/DependencyChecker dead code** — Both are injected into the orchestrator but never invoked in `run_scan`. Wire them into the scheduling path or remove the constructor parameters to avoid confusion.
2. **Unbounded `_available_entities` growth** — Every entity value discovered during a scan is appended to in-memory lists in the scheduler. For scans producing O(10k) entities this means O(10k) strings per type. Consider capping or deduplicating.
3. **Checkpoint resume not implemented** — `ScanConfig.resume=True` is accepted but the orchestrator never reads from a checkpoint file to restore state. Either implement or document as future work.

<summary>Details</summary>

## IncrementalEngine and DependencyChecker not called

The orchestrator's docstring claims integration with `IncrementalEngine` and `DependencyChecker`. Both are accepted as constructor parameters and stored:

```python
self._dependency_checker = dependency_checker or DependencyChecker()
self._output_normalizer = output_normalizer or OutputNormalizer()
```

But nowhere in `run_scan` are they invoked. The scheduler decides eligibility purely on type-level key matching; there's no `dependency_checker.check_tool_ready(tool_spec)` call before scheduling, and no `incremental_engine.should_rerun(...)` call to skip tools that haven't changed. These components are fully implemented and unit-tested in isolation, so this is a wiring gap, not a design gap.

## Swallowed handler exceptions

The `return_exceptions=True` fix prevents cascade failures, but exceptions from handlers are returned as values in the gather result and discarded — `EventBus.publish` doesn't inspect return values. A handler that raises `RuntimeError` produces no log, no metric, no alert. In a system where handlers drive scheduling state transitions (the scheduler's `on_tool_completed` updates `_running_tools` and `_completed_tools`), a silently failing handler could leave the scan in an inconsistent state with no diagnostic signal.

## Entity accumulation in scheduler

`_available_entities` is a `dict[str, dict[str, list[str]]]` mapping scan_id → entity_type → list of all values. Every call to `on_entity_discovered` appends:

```python
self._available_entities.setdefault(scan_id, {}).setdefault(
    event.entity_type, []
).append(event.entity_value)
```

These lists are never deduplicated (a subdomain emitted by two tools appears twice) and never pruned. For the input-building use case, deduplication would save memory and prevent downstream tools from seeing duplicate values in their input lists.

## Test coverage gaps

Not tested: handler exceptions during EventBus dispatch (the `return_exceptions=True` behavior has no assertion), the checkpoint resume path, IncrementalEngine integration with the orchestrator (only unit-tested in isolation), DependencyChecker integration with the orchestrator, host-semaphore eviction behavior, and orchestrator behavior when the same entity type is discovered by multiple tools (deduplication/accumulation).
