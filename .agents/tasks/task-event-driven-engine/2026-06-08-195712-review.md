# Event-driven execution engine for Recontool

The change adds a complete event-driven orchestration layer (`recontool/engine/`, 14 modules) alongside the existing linear `ReconPipeline`. Tools now execute when their input dependencies are satisfied rather than by fixed phase ordering. The architecture is event-bus-centric: an `EventBus` dispatches typed lifecycle events that a scheduler, executor, pending-key store, and incremental engine consume to drive convergence. The existing adapter base class is extended with optional contract methods (backwards-compatible no-ops), and a reference implementation on the `CrtSh` adapter demonstrates the full contract.

Watch for:
- **Orchestrator idle-exit race** (confirmed): the `run_scan` main loop breaks after 3 idle cycles with no convergence check bypass, which can cause premature scan termination when tool execution is slow relative to the 10ms sleep.
- **State leak across scans** (confirmed): `EventDrivenOrchestrator` stores per-scan results in instance dicts (`_scan_results`, `_entities_discovered`) but never cleans them up after `run_scan` returns.
- **Scheduler internal access from orchestrator** (confirmed): the orchestrator checkpoint block reads `scheduler._completed_tools` directly, coupling it to private implementation details.

## High-level view

The EventBus is a thin `asyncio.gather`-based dispatcher with exact-type matching. It carries all inter-component communication and is the single coupling point between the scheduler, executor, and pending-key subsystem. A slow or crashing handler blocks the publish call and can stall the entire event pipeline since there is no error isolation in the gather.

The scheduler maintains in-memory per-scan sets (available keys, running/completed/blocked tools) and uses them to decide tool eligibility. Tools are eligible when their consumed input types appear in the available-key set. This is type-level matching only; the scheduler does not track individual entity values, which means it cannot gate on "at least N entities of type X" and cannot pass discovered values through to downstream tool inputs.

The parallel executor implements three-layer semaphore gating (global, per-tool, per-host). The host semaphore is extracted heuristically from job inputs by checking for `host`, `target`, or `domain` keys. Jobs whose inputs don't match these keys bypass per-host limiting entirely.

The pending-key store persists to the DB but the scheduler and orchestrator don't use it during the main loop; they rely on in-memory event state instead. The PendingKeyStore is not wired into the orchestrator's convergence path, making it a persistence layer for audit rather than a runtime gate.

The incremental engine uses SHA-256 fingerprints of inputs and config to decide whether a tool needs re-execution. Config fingerprinting stores the result in the `output_fingerprint` column on `ToolRun`, overloading that column's semantic meaning and creating confusion about what it actually stores.

6. **Per-host semaphore unbounded growth** — `_host_semaphores` dict in `ParallelExecutor` creates a new semaphore for every unique host string and never evicts.

8. **Adapter contract method duplication** — `emit_normalized_events` and `map_outputs_to_entities` are semantically identical in the reference implementation. Consolidate or have one delegate to the other.

## Orchestrator convergence and idle-exit race

The `run_scan` main loop in `orchestrator.py` drains the scheduler's job queue, executes batches, then increments an `idle_cycles` counter when no jobs are available. After 3 idle cycles (each separated by a 10ms sleep), it breaks out unconditionally:

```python
if idle_cycles >= max_idle_cycles:
    break
await asyncio.sleep(0.01)
```

If a tool execution takes longer than 30ms and produces events that would unblock new tools, the loop may have already exited. The `check_convergence` call at the top of the loop only checks whether tools are running *at that instant*, but the scheduler's `on_tool_completed` handler updates state asynchronously via the bus. In production with real tool latencies this loop will under-schedule. The fix is to check `not scheduler._running_tools.get(scan_id)` (or a public equivalent) before breaking on idle.

## State accumulation in the orchestrator

`EventDrivenOrchestrator.__init__` creates `self._scan_results: dict[str, ScanResult]` and `self._entities_discovered: dict[str, int]`. These are populated during `run_scan` but never pruned afterward. If the orchestrator instance is reused for multiple scans (which the API permits), these dicts grow monotonically. A `del self._scan_results[scan_id]` at the end of `run_scan` (after extracting the result) would fix this.

## EventBus error handling

`EventBus.publish` gathers all handlers:

```python
await asyncio.gather(*(h(event) for h in handlers))
```

If any handler raises, `gather` propagates the first exception and cancels remaining coroutines. A buggy subscriber prevents other handlers from seeing the event. The executor's `execute_batch` correctly uses `return_exceptions=True` for its gather, but the bus does not. This is particularly dangerous because the scheduler subscribes to the same bus as user-provided handlers.

## Fingerprint column overload

`IncrementalEngine.should_rerun` does:

```python
if tool_spec is not None and last_run.output_fingerprint:
    new_config_fp = fingerprint_config(tool_spec)
    if has_changed(last_run.output_fingerprint, new_config_fp):
        return True
```

This compares the tool's *config* fingerprint against the `output_fingerprint` column, implying that column must be written with `fingerprint_config(...)` rather than an actual output fingerprint. The column name is misleading; a separate `config_fingerprint` column would make the model self-documenting.

## Per-host semaphore memory

`ParallelExecutor._get_host_semaphore` creates a `Semaphore` per unique host string extracted from inputs. Over a large scan discovering thousands of subdomains, this dict grows without bound. Each `asyncio.Semaphore` is lightweight (~200 bytes) but the pattern has no eviction and the dict lifetime equals the executor's lifetime. For a scan producing 10k hosts, that's ~2MB of semaphore objects that remain allocated.

## Adapter contract: emit vs map duplication

The extended adapter contract has both `emit_normalized_events(parsed)` and `map_outputs_to_entities(parsed)`. In the CrtSh reference implementation, both return identical output:

```python
def emit_normalized_events(self, parsed):
    events = []
    for subdomain in parsed.get("subdomains", []):
        events.append(Event.asset(self.name, "subdomain", subdomain))
    return events

def map_outputs_to_entities(self, parsed):
    events = []
    for subdomain in parsed.get("subdomains", []):
        events.append(Event.asset(self.name, "subdomain", subdomain))
    return events
```

The intent distinction between these two methods is undocumented in code. Future adapter authors will either implement only one or duplicate logic. Consolidating or having one delegate to the other prevents drift.

## Scheduler type-level key matching and empty inputs

The scheduler tracks available keys as `set[str]` of key *types* (e.g., `{"domain", "subdomain", "live_host"}`). Tool eligibility is determined by whether any consumed types appear in this set. A tool consuming `live_host` will be scheduled the moment *any* live_host is discovered. More critically, `on_tool_completed` schedules eligible tools with `inputs={}`:

```python
eligible = self.select_eligible_tools(scan_id)
for tool_spec in eligible:
    await self.schedule_tool(scan_id, tool_spec.name, {})
```

Downstream tools receive no information about which entities triggered them. The E2E test works around this because the execute_fn ignores inputs and hardcodes behavior, but real adapters will need their inputs populated.

## Test coverage gaps

Not tested: error propagation through the EventBus (handler exceptions during publish), orchestrator behavior when `execute_fn` raises intermittently during a batch, the interaction between `IncrementalEngine` and the orchestrator loop (the incremental engine is unit-tested in isolation but never called from the orchestrator), and checkpoint resume (the `config.resume` flag is accepted but the resume path is never implemented or tested).
